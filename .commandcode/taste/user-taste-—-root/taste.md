# User Taste — root
- Writes in Japanese and expects replies in Japanese (technical terms may stay in English). Confidence: 0.9
- Gives very terse approvals ("計画読みました / 続行お願いします", "OK、実際の実装に入れますか", a bare "お願いします" to a proposal that ended by asking permission to proceed with the *conservative* next step) and expects work to start immediately — do not re-litigate settled decisions or ask further scoping questions once a plan is accepted. Confidence: 0.65
- Strong preference for self-hosted infrastructure over public third-party services (runs their own Invidious/Docker server rather than relying on public instances). Values stability of a controlled endpoint. Confidence: 0.7
- Comfortable with a long planning phase before implementation on large, ambiguous projects: wants environment feasibility verified and the architectural direction settled up front. Confidence: 0.6
- Actually flashes the built artifact onto the device and comes back with the bare on-device result (e.g. just an error code like `800200D9`, or a verbatim console string like "データが壊れています"); expects a root-cause diagnosis, a fix, and a rebuilt artifact to retry — not a discussion of possibilities. Confidence: 0.8
- Reports only the observed failure and trusts the agent to investigate; no hand-holding or scoping questions wanted at that point. Recurs verbatim across fixes — e.g. a whole message of just "まだ8002013Cエラーで起動に失敗しました", i.e. the bare error code and no hint about which of the several in-flight hypotheses was wrong. Confidence: 0.7
- Reports *positive* and null results just as tersely as failures — a whole message of "probeは一切エラーが出ずにXMBに戻されました" (no error, returned to the XMB) with no interpretation of what that means. Do not expect the user to spell out the implication of a clean run; state it yourself and move straight to the next bisection. Confidence: 0.65
- **A bare "起動しました!" names only the milestone it was asked about and nothing more** — it means the module got past the loader and reached `main()`, not that any of the several in-flight features it was supposed to enable now works. Do not ask which subsystem the user meant; instead read the source to find which call sites the new build actually reached (here the newly added `compat_kernel_init()` turned out to be a no-op with the kernel gate never wired at all), then build the instrumentation that will settle the open questions. A single-word success report is a prompt to verify, not a wrap-up. Confidence: 0.7
- Feedback is minimal and undifferentiated when a fix fails — the entire message is "まだ同様のエラーです". Do not expect a hint about what changed or which part is still wrong; on a non-result the user expects the agent to re-derive the root cause from its own prior hypotheses rather than ask what to try next. This holds even when a change made things *worse* ("認識すらできなくなりました") — the user reports the regression and still does not ask for a rollback or a plan; keep debugging. Confidence: 0.8
- In a long debugging loop the user checks in only to hand over the next piece of evidence (a log via `@`, an on-device error code). They do not want progress check-ins between attempts, and a message that ends by asking them to try something and report back is weaker than one that goes and verifies it first — the user replied with terse results across a dozen agent-only iterations, which only works if each turn is self-contained. Confidence: 0.7
- Comfortable being handed a manual A/B experiment (two prebuilt packages, explicit Memory Stick paths, "tell me which one boots and with what error code") as the next step — a bisection split the user can run on hardware is an acceptable form of "proceed". Confidence: 0.6
- Reports **several variants at once** with a single combined verdict ("両方正常起動しました" — "both started normally"), rather than one line per PBP. A one-line summary covering a whole batch counts as a complete answer: draw the conclusion per variant yourself, state it, and move on. Confidence: 0.7
- Reports the result of a *diagnostic-only* variant exactly like a normal build — a bare "8002013Cエラーで起動に失敗しました" with no reminder of which PBP it was or that it was built by subtraction. Treat every PBP you hand over as a first-class A/B: name the file, the Memory Stick path and the two branches each time, and keep your own ledger of which variant tests which hypothesis. Confidence: 0.65
- Answers a multi-variant probe decision table with a **partial one-line result** ("PROBEAのみ起動しました", "PAVのみ起動失敗しました" for a *four*-variant batch): no error code for the variant that failed, no interpretation, no "what next". Any per-variant outcome counts as a complete answer — conclude from it yourself, state the verdict, and roll straight into the next bisection. Batching more variants than two does not prompt more detail. Confidence: 0.7
- Responding to a failed fix with a long recap table of what was verified and ruled out lands well; the diagnosis narrative is the deliverable when the fix does not land. Confidence: 0.6
- Works on retro/embedded homebrew (PSP), targeting real modified hardware — assumes custom firmware and real-device constraints rather than emulator-only assumptions. Verify the actual execution target from artifacts (emulator log, presence/absence of an ISO) rather than trusting the platform as stated: the user once reported an on-device result that turned out to be PPSSPP. Confidence: 0.7
- Hands over primary-source evidence by attaching the file with `@` and a one-line label in Japanese ("PPSSPPでのエラーログです"), expecting the agent to open and read the file itself and derive the answer from it — no request to paste contents or to be told what to look for. Confidence: 0.8
- Treats emulator/host-side logs as first-class debugging input equal to a device error code; a single pasted log file is often enough to end a long debugging loop. Confidence: 0.7
- Reports results from **both** the real device and the emulator in the same terse message ("実機でTESTHELLOは800200D9エラーで起動失敗、YTLEGACYPSPは破損扱いでした"), attaching the log file with `@`. Bundling the two environments' outcomes in one line is enough — no elaboration or interpretation expected. Confidence: 0.7
- Values an explicit self-correction over a quiet patch: admitting the earlier launch-mode hypothesis was premature lands better than silently shipping the fix, as long as the root cause is then pinned exactly. Confidence: 0.6
- Asks "what should it look like if it works as designed?" right after a fix lands — i.e. validates a reimplementation against the **original design's** expected behaviour, not against "no crash". Treat the reference architecture (e.g. a desktop/web version of the same app) as the spec and derive the acceptance criterion from it. Confidence: 0.7
- Explicitly retracting a run of wrong hypotheses ("前回までの私の推測（…）はいずれも的外れでした") is welcome and expected in a debugging handoff — state plainly which fixes were tried and did not land, then say what the comparison against a known-good artifact revealed. Naming the next single experiment and the exact Memory Stick path to copy it to is the accepted hand-off. Confidence: 0.7
- Wants the acceptance criterion made concrete and checkable rather than a qualitative "it should work now": enumerate the designed screen states as ASCII wireframes with exact coordinates, colours and field text, and list the expected log-line sequence as the definition of a successful boot. Note explicitly which state the current build is *not* reaching (e.g. still on the prompt screen because the host is unreachable) so success is not overclaimed. Confidence: 0.7
- **Proactively hands over a working reference implementation of the exact capability being debugged** — here a path to another app's directory plus "PSPのハードウェアデコーダを使用している別のソフトウェアなのですが、これを参考にできますか". This is a deliberate move away from another round of the user's own probe/flash cycle: read the shipped artifact, extract the mechanism, adopt that structure. The request is an invitation to reverse-engineer the reference, not a yes/no question. Confidence: 0.7
- **Re-asserts "出力は日本語でお願いします" explicitly in the message.** The requirement is not satisfied by mostly-Japanese output — when prose drifts into mixed Chinese/English fragments the user re-states it verbatim. Keep the narration strictly Japanese even when quoting identifiers, error strings or prior turns. The drift recurs even in otherwise good long write-ups — a single Japanese report came back with "汇报します", "现阶段の完成度Keeping出荷するか", "機能 Alliance", "他のucidな方法" and other CJK/English word-substitutions spliced into otherwise correct Japanese — and the same drift recurred on the following turn ("Kaiser Kaiser 相当于", "已解决/当前问题", "那里までは OK", "Causes切り分け"), so proofread headings and the final summary paragraph specifically; the middle of a technical answer can be clean while the intro and outro are not. Confidence: 0.75
- **Closes off an option the user has already tested and failed in the real world, in one terse message with concrete symptoms** — "ソフトウェア復号は、フリーズや音ズレが多発し、バッテリーが一瞬で無くなり使い物になりませんでした" (a rejected path, not a boot error: freezes, A/V desync, instant battery drain, stated flatly with no "what next"). An option the user has reported as unusable on hardware is settled, not open for re-proposal — drop it from later option tables and state what is known to remain, rather than offering a "safer" version of something they just said they cannot use. First-hand real-device experience overrides an agent's "recommended" label. Confidence: 0.7
- **Answers a "I cannot do X / X is impossible" conclusion with a single counterexample question, not with a new requirement** — "では、なぜ同じHomebrewプロジェクトのGotubeはハードウェアデコードを実装出来ているのですか". The counterexample is the *same* artifact the agent has already been reverse-engineering, re-labelled into the agent's own category, which is the sharpest way to attack a negative claim. Do not re-assert the negative or accept the user's reclassification as given: either refute it with evidence from the artifact, or state plainly that the earlier negative claim was overstated and retract it. Confidence: 0.7
- **Deflects a ship-or-stop checkpoint by challenging its premise instead of choosing.** When the agent closes a long effort with "how should I proceed — ship at this completion level, or abandon?", the user ignores the decision entirely and interrogates the technical claim the decision was predicated on. Treat a closing decision request as an invitation to re-open the reasoning, not as a question awaiting an answer. Confidence: 0.6
- **When handed an explicit option table with a "recommended" safe path and a technically ambitious one, picks the ambitious path** — chose implementing a kernel-mode bridge over a software H.264 decoder even after being warned the kernel route is proprietary-interface, CFW-dependent and likely to break on newer firmware. Favours fidelity to how the real thing works over a path that merely works. Confidence: 0.6
- **But re-evaluates immediately when handed concrete disassembly evidence — the choice is about the goal, not a fixed preference for ambition.** Asked to pick between writing a kernel-mode bridge from scratch, reusing GoTube's bridge, probing on hardware, or shipping without playback, the user chose "build the bridge myself"; one turn later, after the `attributes=0x1006` kernel-mode bit was read out of the bridge PRX's module info, the same user chose "measure the actual behaviour on the device" and dropped self-authoring. So present the decisive hard data (a mode bit, a disassembly excerpt) alongside the option table and expect the answer to change — do not treat an earlier pick as a settled commitment, and do not re-litigate it either. Confidence: 0.6
- **Corrects an "impossible" claim by naming their own environment, not by arguing** — one terse message, "少なくとも私のHomebrew環境(PRO CFW最新版)ではGoTubeのハードウェアデコードは正常動作しています". This supplies a constraint the agent had been missing rather than debating the conclusion, so treat it as invalidating the environment assumption the impossibility rested on: re-open and implement, do not re-present the argument or re-ask the same option table. Naming the specific CFW flavour and version is the useful part — scope feasibility claims to the user's stated environment instead of asserting a platform-wide limit. Confidence: 0.65
- **Wants the redistribution/licensing boundary raised unprompted, then picks the "don't bundle it" architecture.** When the fix required shipping a third party's proprietary kernel-mode binaries, the agent flagged the copyright problem on its own and offered personal-use-only / dynamic-load-at-runtime / source-only; the user chose dynamic load. Surfacing the legal limit without being asked, and then immediately supplying a packaging design that keeps the feature working inside it, is the accepted move. Confidence: 0.7
- **A licensing objection is a reason to change the packaging, not to drop the capability.** Having already been offered a "ship without playback" path, the same user went back to the kernel-module route once it was reframed as "read a file that is already on my own Memory Stick". The appeal is reaching the real hardware capability; what blocks it is redistribution, not risk. Frame the options around what the goal requires and how the artefact is delivered, not around which is the safer recommendation. Confidence: 0.65
- **States the *display* result as a bare clause beside the log handover, and genuinely cannot read the screen when rendering is broken** — "@…/boot.log ログです / 画面はバグって .search プロンプトはわかりませんでした". So an acceptance criterion phrased as "you should see `START search` on screen" is not confirmable while the display is faulty, and no photo will be coming; always pair the visual criterion with a log-line criterion (e.g. `[net] loaded flash0:/kd/net.prx`) that the user can answer by re-attaching the boot log. Confidence: 0.7
- **Reports a partial fix as a two-part verdict in one clause — what cleared, what did not** — "乱れなくはなりましたが、暗転したままになりました" (no longer garbled, but still a black screen). The first half is a correction of what the agent said last turn, not praise: an agent verdict of "the screen is fine" is treated as unverified until the log agrees, and the user's line is the evidence. Read the appended log first and reconcile it against the previous claim before narrating anything new; do not restate the milestone that the user just contradicted. Confidence: 0.75
- **A new symptom reported by the user is a fresh branch, not the old failure resurfacing.** "Screen no longer garbled, now black" says the previous hypothesis *was* right and the bug simply moved one stage later — acknowledge that explicitly, then attack the new stop point (`[boot] gu ready` with nothing after it) rather than re-litigating the pitch fix. Confidence: 0.7
- **A terse regression report ("再び乱れるようになりました") names a symptom the agent already declared fixed — read it as "your intervening change broke it", not as a new bug.** The same log comes back attached with a three-word verdict and no hypothesis. The useful move is to diff what changed since the last good build (here: diagnostic log markers and a `sceGuFinish()` added then removed for being wrong), because an agent-introduced intermediate edit is the usual cause of the return. Say which change is being reverted and do not re-narrate the earlier diagnosis. Confidence: 0.7
- **Re-attaches the *same* log file with a bare "still <symptom>" when a fix does not land** — the path and label are identical to the previous turn, and the new verdict line is three words. Treat this as: the rebuild is on the device, the same failure persists, and the log has *new* lines worth reading (here the load attempts with `0x80010002`, which the previous turn could not have known). Read the appended lines for what changed, state which hypothesis the evidence kills, and ship the next build — do not ask for a fresh log, and do not restate the previous plan. Confidence: 0.75
