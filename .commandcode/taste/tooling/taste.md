- `psp-fixup-imports: stubs out of order` is **real and fixable — do not dismiss it as toolchain noise.** It is easy to misjudge: it also fires on a from-scratch hello-world and survives naive `pspuser`-first/last permutations and dropping `-Wl,-q`, which makes it look like a pre-existing build artifact. The actual cause is a *duplicated library scan*. `psp-gcc -dumpspecs` shows the driver appends after your `target_link_libraries` list: `-lm --start-group -lpthreadglue -lpthread -lcglue -lc --end-group` then `-lpsputility -lpsprtc -lpspnet_inet -lpspnet_resolver -lpspsdk -lpspmodinfo -lpspuser -lpspkernel`. Listing any of those yourself (notably `pspuser` and `lc`) makes the archive get scanned twice, so its stubs land in two non-contiguous runs — which is precisely what "stubs out of order" reports. Drop them from the explicit list; after that the warning vanished and all 84 imported functions resolved to valid NID/stub pointers. Correlate with a boot-time `Unknown syscall (module 255 func 4095)`, which is the symptom of the second run's NID pointers being left unset and means malloc/stdio/threads are all unresolvable. Also re-check that `psp-fixup-imports` is still in the POST_BUILD chain — removing `create_pbp_file` silently removes the fixup and strip steps with it. Confidence: 0.8
- **Link at a real user-memory base, not 0.** The SDK's `linkfile.prx` starts the image at address 0, so the ELF comes out `ET_EXEC` with segments at vaddr 0. The loader honours that: it computes `bRelocate = (e_type != ET_EXEC)`, so with `ET_EXEC` it calls `AllocAt(loadAddress + totalStart, ...)` and — because `PSP_GetDefaultLoadAddress()` always returns 0 — asks for a block at address **0**, outside user memory (`0x08800000`–`0x0A000000`). That is the real cause of the startup `0x800200D9` / `Block Allocator (08800000-0a000000) failed` / `AllocAt failed :( 00000000`. Copy the SDK's `linkfile.prx` and change only `PROVIDE (__executable_start = 0x0); . = 0x0;` to `0x08804000`; in CMake, do it with `file(READ)` + `string(REGEX REPLACE)` + `file(WRITE)` and point `-T` at the generated script. This change is what produced the first successful boot. Confidence: 0.85
- You can test a PBP end-to-end **without the user and without hardware** by driving PPSSPP headlessly: the AppImage is mounted at a `/tmp/.mount_PPSSP...` directory while running, and `$MOUNT/bin/PPSSPPSDL <path-to-game-dir>` boots it under `timeout`. Redirect stdout to a file and grep with `grep -a` — piping straight into a pipe mangles the output, and the logs contain non-UTF-8 bytes that need the binary-safe flag. A `N[BOOT]: Booted <path>` line is the definitive "it works" signal; `JIT` compiling `0882xxxx` addresses confirms your own code is executing. This turns the previous "please reboot PPSSPP and tell me what you see" round trip into a check the agent can run itself. Confidence: 0.85
- When reading a loader's source to reverse-engineer a file format, do not trust the enum/field names — go read the **actual arithmetic** at the failure site. `PBPReader.h` exposes `PBP_EXECUTABLE_PSP = 6` and sizes it as `offsets[7] - offsets[6]`, while `__KernelLoadModule` uses slot 5 and 6 as a start/end pair; the enum names are misleading and cost several rounds of wrong fixes. Re-read the exact comparison expressions (`offsets[6] > fileSize`, `offsets[5] > offsets[6]`) and reimplement them verbatim in a script before changing the artifact. Confidence: 0.8
- Reversing an offset table: when a fix "should" work but the loader still fails, check whether the field layout has a **hole** rather than assuming a uniform stride. The contiguous write was only wrong because the reader skips `0x0C` and resumes at `0x10`; simulating the reader's byte offsets in Python surfaced the four-byte shift immediately. Confidence: 0.75
- `CreatePBP.cmake` hardcodes `mksfoex -d MEMSIZE=1`, and the loader reads PARAM.SFO's MEMSIZE as the module's heap ceiling in 64 KB units. **Do not "fix" this to 0.** A stock PBP capped at 64 KB produced `0x800200D9` (`SCE_KERNEL_ERROR_MEMBLOCK_ALLOC_FAILED`, defined in `psp/sdk/include/pspkerror.h`) at startup — but that error was a red herring: the real cause was the zero-size `data.psp` slot in the PBP header, plus the image linked at base address 0. Rewriting PARAM.SFO with `MEMSIZE=0`/`REGION=0`/`BOOTABLE=0` while the header was still wrong made a previously-bootable PBP report as "データが壊れています". Leave the SDK defaults in place and fix the packaging and link base instead. Confidence: 0.7
- `pack-pbp` arity is strict and the SDK macro gets it wrong. The verified-correct call is `pack-pbp out.pbp param.sfo NULL NULL NULL NULL NULL NULL <elf>` — six `NULL` placeholders for icon0/icon1/pic0/pic1/snd0/psar, ELF last, and **no** trailing PSAR argument. Adding a ninth trailing `NULL` makes the tool reject the whole invocation. `CreatePBP.cmake` calls it with one placeholder too few, which parks the ELF in the wrong slot and leaves the PBP header's `psp_elf` field pointing past EOF. When hand-rolling a repack step, match the verified six-NULL form, not the macro. Caveat: the six-NULL PBP was also seen *loading* successfully once, and later rejected as corrupt while structurally byte-perfect — so arity explains one failure mode, not every "データが壊れています". Confidence: 0.6
- Verifying a PBP without hardware: the header is `\0PBP`, a u32 version, then a sub-file offset table. **The table is NOT contiguous**, which is the part that is easy to get wrong: `offsets[0]` lives at byte `0x08`, byte `0x0C` is padding the loader skips, and `offsets[1]` onward start at `0x10`. The loader derives the entry count as `numfiles = (offsets[0] - 8) / 4`, so `offsets[0] == 8 + 4*numfiles`.
- The PBP offset-table slots are a *start/end* pair for the executable, not "the start of the next file". PPSSPP's `__KernelLoadModule` reads the ELF as the range `offsets[5] .. offsets[6]`: slot 5 is where `data.psp` begins, slot 6 is where it ends (normally the file size). Slot 7 is `data.psar`, left at 0. Emptied asset slots (icon0/1, pic0/1, snd0) all alias the ELF start so their computed size is zero. Earlier beliefs that the ELF belonged in slot 6 with `size = offsets[7] - offsets[6]` were wrong — that arrangement makes the loader's `offsets[5]..offsets[6]` range empty and it reports `ELF file truncated - can't load`. This layout was confirmed by an actual successful boot, so prefer it over the spec-derived guess.
- The SDK's `pack-pbp` writes the executable into the wrong slot, which is why stock PBPs are rejected. Do not hand-check magic bytes at an offset: the rejected PBP had a valid `\x7fELF` sitting exactly where a quick check looks for it. Instead reproduce the loader's exact arithmetic in a throwaway script — `numfiles`, the `12 + 4*numfiles > fileSize` bound, `offsets[6] > fileSize`, `offsets[5] > offsets[6]`, then `elfSize = offsets[6] - offsets[5]`, plus ELF magic in that range and a byte-compare against the linked output — and assert on the result before shipping. PARAM.SFO is a 20-byte header with 16-byte index entries starting at offset 20 (`key_idx u16, fmt u16, len u32, max u32, data_off u32`), terminated by `key_idx == 0xFFFF`. Confidence: 0.85

Absence is a strong candidate for a loader-level rejection. Confidence: 0.6

- When an emulator reports a load failure that the host-side artifact looks clean, go read the emulator's **own source** for the file-format reader (`PBPReader.cpp`/`.h` on raw.githubusercontent.com) and reimplement its exact size/offset arithmetic against the artifact. - **In this old-generation `libpspgu`, a display list must be open before any state call.** `libpspgu` is a static user-space library, not syscall-backed: `sceGuStart(ctype, list)`'s second argument is the real memory the GE command stream is written into. Consequences, all verified on hardware-equivalent boot: (1) passing `NULL` makes every subsequent `sceGuDrawArray` write through address 0, giving an immediate infinite `Bad memory access 00000004` loop and a hard freeze — allocate a 16-byte-aligned list (e.g. `memalign(16, ...)`). (2) `sceGuDrawBuffer`, `sceGuOffset`, `sceGuViewport`, `sceGuScissor`, `sceGuEnable`, `sceGuTexFunc/TexFilter/TexWrap/ClearColor`, `sceGuTexImage` and the depth/alpha/blend calls all record into `gu_list`; calling them in an `init` function with no list open is the `Bad memory access 00000004` fault. Only `sceGuInit` and `sceGuDispBuffer` are safe before `sceGuStart`. (3) Persistent render state must therefore be re-emitted inside every frame — put it in `gui_start_frame()` after `sceGuStart`, and in `gui_end_frame()` do `sceGuFinish` → `sceGuSync` → `sceGuDisplay` → `sceGuStart` → `sceGuDrawBuffer` → rebind texture, in that order. Confidence: 0.85
- **A boot-time log file on the Memory Stick is the fastest way to localise a crash on a device you cannot see.** Mirroring the on-screen debug output into `ms0:/PSP/GAME/<pkg>/boot.log` (truncate in `log_init`, append per `log_printf`) turns "it crashes somewhere after boot" into an exact stop point: bisect by adding a `log_printf` between each init call and reading back the last line printed. This found two consecutive faults (a missing display list, then a texture bind before any list was open) that neither the emulator's `Bad memory access` count nor a segment-size inspection could localise. Cheaper than screenshots, and works identically on real hardware. **Corollary: read the whole log before narrating any verdict — including a success one.** A turn that reported "the screen is fixed" on the strength of the user's "no longer garbled" was contradicted by the very log the user had just attached, which stopped at `[boot] gu ready`; the next turn had to retract it. The last line of the log is a harder fact than the user's paraphrase of what they saw, so open the file first and let it bound the claim. Confidence: 0.8

- **`pspSdkInstallNoPlainModuleCheckPatch()` must be removed from a homebrew link — it adds a `LoadCoreForKernel` import — but removing it was *not* what fixed `0x8002013C`.** The call drags `libpspsdk`'s `InstallNoPlainModuleCheckPatch.o` into the link; that object references `sceKernelProbeExecutableObject`, which adds a `LoadCoreForKernel` import (loadcore.prx, kernel-mode, never loaded by the XMB for an EBOOT.PBP) and the whole module is then rejected before `main()`. `-lpspsdk` is auto-appended by the gcc SPECS, so the library cannot simply be dropped from the link line — the only fix is to stop referencing the symbol. General rule: with a static archive, referencing one symbol pulls in that entire object *and its transitive imports*, so an innocuous convenience call can silently change the module's import table. Still worth doing, but the same error code persisted afterwards on hardware — do not treat it as the confirmed root cause. Confidence: 0.8
- **To find which object introduces a bad import entry, sweep the archives, not the sources.** `ar x libX.a` into a scratch dir, then per `.o` run `nm -g "$o" | awk '$1=="U"{print $2}'` and grep for the offending symbol. Compile the project's own `.c` files with `psp-gcc -c` and check them first, then loop over every linked SDK archive; here the project sources were clean and the culprit was an SDK archive that only the sweep found. Also dump the import table only after a clean `rm -rf build` rebuild — a stale ELF reported an import that the current sources no longer produced and sent the search after already-removed code. Confidence: 0.8
- **Preloading a module from `main()` cannot fix an import-table failure.** The loader resolves imports before `main()` is entered, and `pspSdkInstallNoPlainModuleCheckPatch()` only relaxes the device check that governs *where* you may load from — it does not alter the import table, and in practice it was the thing that *created* the unresolvable entry. Time spent on a `sceKernelLoadModule`/`sceKernelStartModule` self-load preamble for an unresolved import is wasted; go fix the table. Note also that a failed self-load is expected under an emulator (no `flash0:`), so don't treat it as a regression. Confidence: 0.85
- **Rebuilding a stale SDK archive from upstream source is not automatically a fix — verify at the artifact level.** Replacing the shipped `libpspgu.a` with one rebuilt from current PSPSDK `src/gu/*.c` left `Kernel_Library` in the import table unchanged, because the *header* decides the recorded module: in that SDK `sceKernelCpuSuspendIntr` is declared only in `pspintrman.h` (a kernel-mode import), not `pspuser.h`.
